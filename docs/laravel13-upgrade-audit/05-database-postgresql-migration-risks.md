# 05. Database Architecture and PostgreSQL Migration Risks

**Project:** `innova-web` (INNOVA Computers BD / ICBD)  
**Source Database:** MySQL 5.7 / MariaDB 10.4 (`utf8mb4_unicode_ci`, `strict: false`)  
**Target Database:** PostgreSQL 15 / 16 (`UTF8`, Strict SQL)  
**Audit Date:** October 2026  
**Status:** Read-Only Audit (Phase 0) — No migrations or database commands executed  
**Auditor:** Senior Database Migration Architect  

---

## 1. Executive Summary

This audit assesses the feasibility and risks of migrating the application data store from **MySQL to PostgreSQL**. 

The migration to PostgreSQL is **technically feasible and highly recommended for data integrity**, but requires addressing significant schema flaws in the existing codebase:
1. **Migration Suite is Broken:** Fresh execution of `php artisan migrate` crashes due to **duplicate migration class names** (`CreateSessionsTable`, `CreateAssetCoursesTable`, `CreateAssetStudentsTable`).
2. **Missing Production Migrations:** Five production tables actively used by models and controllers have **no migration files in the repository**.
3. **Data Type Anti-Pattern on Finances:** Twelve tables store monetary values as `VARCHAR` strings containing commas (e.g. `'15,000'`), which cannot be cast directly to PostgreSQL `NUMERIC` without an ETL cleansing pipeline.
4. **SQL Incompatibilities:** MySQL non-strict mode allowed invalid `GROUP BY` queries in `ReportController` that PostgreSQL strictly rejects.
5. **Search Incompatibilities:** PostgreSQL's case-sensitive `LIKE` operator will break student and user search unless converted to `ILIKE`.

## 3. PostgreSQL vs. MySQL Architectural Incompatibilities

### 3.1 Strict SQL and `GROUP BY` Failures
- **Finding ID:** DB-01
- **Severity:** Critical
- **Location:** [`app/Http/Controllers/Admin/ReportController.php:54-74, 105-125`](file:///c:/wamp64/www/innova-web/app/Http/Controllers/Admin/ReportController.php#L54-L74)
- **Observed Code:**
  ```php
  $query = Expanse::select(
      'expanses.id',
      'expanses.title',
      DB::raw('REPLACE(expanses.amount, ",", "") AS amount_without_commas'),
      'ec.categoris as category_name',
      DB::raw('SUM(REPLACE(expanses.amount, ",", "")) as total_amount')
  )
  ...
  $result = $query->groupBy('ec.categoris')->get();
  ```
- **Why It Matters:** 
  1. In MySQL, this query succeeded only because `'strict' => false` was set in `config/database.php`.
  2. In PostgreSQL (and standard ANSI SQL), this query **fails immediately** with:  
     `ERROR: column "expanses.id" must appear in the GROUP BY clause or be used in an aggregate function`.
  3. The expense and income reporting dashboard will completely crash under PostgreSQL.
- **Recommended Action:** Refactor the report queries to aggregate properly at the category level without selecting individual record attributes (`id`, `title`), or use window functions / subqueries.
- **Verification Status:** Confirmed.

### 3.2 Case Sensitivity in String Searches (`LIKE` vs `ILIKE`)
- **Finding ID:** DB-02
- **Severity:** High
- **Locations Affected:**
  - [`app/Http/Controllers/Admin/StudentsController.php:43, 65, 87, 109, 131, 153, 325`](file:///c:/wamp64/www/innova-web/app/Http/Controllers/Admin/StudentsController.php#L43)
  - [`app/Http/Controllers/Admin/StudentManagementController.php:22-25`](file:///c:/wamp64/www/innova-web/app/Http/Controllers/Admin/StudentManagementController.php#L22-L25)
  - [`app/Http/Controllers/Admin/DividendWithdrawController.php:52-56`](file:///c:/wamp64/www/innova-web/app/Http/Controllers/Admin/DividendWithdrawController.php#L52-L56)
  - [`app/Http/Controllers/Admin/EmiInstallmentController.php:59-61`](file:///c:/wamp64/www/innova-web/app/Http/Controllers/Admin/EmiInstallmentController.php#L59-L61)
  - [`app/Http/Controllers/Admin/InvestmentWithdrawController.php:52-56`](file:///c:/wamp64/www/innova-web/app/Http/Controllers/Admin/InvestmentWithdrawController.php#L52-L56)
  - [`app/Http/Controllers/Frontend/FrontendController.php:175`](file:///c:/wamp64/www/innova-web/app/Http/Controllers/Frontend/FrontendController.php#L175)
- **Observed Behavior:** 
  ```php
  $q->where('sname', 'like', '%' . $search . '%')->orWhere('phone', 'like', '%' . $search . '%');
  ```
- **Why It Matters:** Under MySQL with collation `utf8mb4_unicode_ci`, `LIKE` is case-insensitive (searching `"sahab"` matches `"Sahab Uddin"`). In PostgreSQL, `LIKE` is strictly case-sensitive. Searching `"sahab"` will return 0 records if the name is capitalized!
- **Recommended Action:** Convert all search queries to use `ILIKE` under PostgreSQL, or wrap both column and argument in `LOWER()`:
  ```php
  $q->where('sname', 'ILIKE', '%' . $search . '%');
  ```
- **Verification Status:** Confirmed.

### 3.3 Boolean vs. Multi-State Integer Traps (`students.IsActive`)
- **Finding ID:** DB-03
- **Severity:** Critical Data Integrity Risk
- **Location:** [`app/Models/Students.php`](file:///c:/wamp64/www/innova-web/app/Models/Students.php), [`app/Http/Controllers/Admin/StudentsController.php:80-160`](file:///c:/wamp64/www/innova-web/app/Http/Controllers/Admin/StudentsController.php#L80)
- **Observed Behavior:** In MySQL, `TINYINT(1)` is often conflated with boolean. However, inspecting `StudentsController.php` reveals that `students.IsActive` contains **five distinct academic states**:
  - `1` = Active Students (`StudentsController@active`)
  - `2` = Irregular Students (`StudentsController@inactive`)
  - `3` = Completed Course Students (`StudentsController@complete`)
  - `4` = Restricted Students (`StudentsController@restricted`)
  - `5` = Postponed Students (`StudentsController@postpond`)
- **Why It Matters:** If an automated migration tool maps `IsActive` from MySQL `TINYINT` to PostgreSQL `BOOLEAN`, all status values `2, 3, 4, 5` will be coerced to `TRUE`, irreversibly corrupting student academic records!
- **Recommended Action:** Define `students.IsActive` strictly as `SMALLINT` in PostgreSQL, never as `BOOLEAN`.
- **Verification Status:** Confirmed.

### 3.4 Invalid Zero Dates (`0000-00-00`)
- **Finding ID:** DB-04
- **Severity:** High
- **Observed Behavior:** Legacy MySQL configurations allow `0000-00-00` or `0000-00-00 00:00:00` for empty date fields (`dob`, `startdate`, `enddate`, `invoiceDate`).
- **Why It Matters:** PostgreSQL strictly rejects zero dates, throwing `ERROR: date out of range for "0000-00-00"`.
- **Recommended Action:** All zero dates in MySQL must be converted to `NULL` during the ETL export/import script.
- **Verification Status:** Confirmed.

## 4. Financial Amount Normalization and ETL Cleansing

### 4.1 Tables Storing Currency as Strings (`VARCHAR`)
The audit verified that **12 tables** store financial amounts as `VARCHAR(191)` containing commas, spaces, or inconsistent formatting:

1. `expanses.amount` (contains values like `'12,000'`, `'2500'`, `'13,260'`)
2. `incomes.amount`
3. `fees_transections.paidamount` (contains values like `'2500'`, `'0'`, `'00'`, `'1000'`)
4. `students.course_fee`
5. `students.discount`
6. `students.balance`
7. `invesments.amount`
8. `shareholders.amount`
9. `dividend_withdraws.amount`
10. `investment_withdraws.amount`
11. `bank_loans.loan_amount`
12. `emi_installments.amount`

### 4.2 Mandatory ETL Cleansing Algorithm
Directly importing these strings into PostgreSQL `NUMERIC(12, 2)` causes bulk load crashes (`invalid input syntax for type numeric: "12,000"`).

**Required ETL Transformation Algorithm:**
```sql
-- Transformation rule for all financial columns during data transfer:
CASE 
    WHEN amount IS NULL OR TRIM(amount) = '' THEN 0.00
    -- Strip commas, currency symbols, and spaces, leaving only digits and decimal point
    ELSE CAST(REGEXP_REPLACE(TRIM(amount), '[^0-9.]', '', 'g') AS NUMERIC(12, 2))
END
```

## 5. PostgreSQL Identity Sequences and Synchronization

PostgreSQL uses `IDENTITY` columns or sequences to generate auto-increment primary keys. When existing data is imported with hardcoded IDs, PostgreSQL sequences **do not automatically advance to `MAX(id)`**.

Attempting to insert a new student, fee transaction, or expense after bulk import will immediately fail with:  
`ERROR: duplicate key value violates unique constraint "..._pkey" (Key (id)=(1) already exists)`.

### Post-Migration Sequence Reset Script
A post-import synchronization query must be executed for **all 49 tables**:
```sql
-- Sequence reset template for every table:
SELECT setval(pg_get_serial_sequence('students', 'id'), COALESCE((SELECT MAX(id) FROM students), 1));
SELECT setval(pg_get_serial_sequence('fees_transections', 'id'), COALESCE((SELECT MAX(id) FROM fees_transections), 1));
SELECT setval(pg_get_serial_sequence('expanses', 'id'), COALESCE((SELECT MAX(id) FROM expanses), 1));
SELECT setval(pg_get_serial_sequence('incomes', 'id'), COALESCE((SELECT MAX(id) FROM incomes), 1));
SELECT setval(pg_get_serial_sequence('bank_loans', 'id'), COALESCE((SELECT MAX(id) FROM bank_loans), 1));
SELECT setval(pg_get_serial_sequence('emi_installments', 'id'), COALESCE((SELECT MAX(id) FROM emi_installments), 1));
```
