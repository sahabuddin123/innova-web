## 1. Executive Strategy & Guiding Principles

The migration of `innova-web` from MySQL to PostgreSQL must achieve **zero data loss, zero password resets, and 100% financial reconciliation**.

### Non-Negotiable Preservation Guarantees:
1. **Zero Password Resets:** All 7 administrative accounts (`admins`) and 149 student portal user accounts (`users`) store industry-standard `$2y$10$` Bcrypt password hashes. These hashes are 100% natively compatible with Laravel 13 on PostgreSQL. No user or administrator will be forced to reset their password.
2. **Preservation of Auto-Increment Primary Keys:** All primary keys (`id`) from 1 to 15,663 across all 52 tables will be imported verbatim using `IDENTITY` bypass, ensuring all foreign-key relationships remain intact.
3. **100% Financial Reconciliation:** The aggregate sums of all student fee receipts (1,604 rows), expenditures (6,338 rows), incomes (5,694 rows), shareholder capital investments (46 rows), bank loans (7 rows), and EMI payments (71 rows) must match down to the exact paisa before and after migration.
4. **Preservation of Media File References:** Disk file paths stored in `students.image`, `teachers.image`, `expanses.image`, `incomes.image`, `galleries.image`, `sliders.image`, and `asset_registrations.photo` are relative paths (e.g. `stuff/Rn9g0Ag...png`). Verbatim preservation ensures zero broken images in `storage/app/public/`.
5. **Bangla Unicode Integrity:** Student names, guardian details, addresses, and course descriptions written in Bangla (Bengali script) will be verified using Unicode normalization (`NFC`) to prevent font corruption.

## 4. Financial Reconciliation & Validation Rules

Financial figures must be reconciled across MySQL and PostgreSQL using identical aggregate queries:

### 4.1 Checksum Query 1: Student Fees Collected
```sql
-- MySQL Source:
SELECT 
    COUNT(*) as total_records,
    SUM(CAST(REPLACE(paidamount, ',', '') AS DECIMAL(15,2))) as total_paid_amount
FROM fees_transections;

-- PostgreSQL Target:
SELECT 
    COUNT(*) as total_records,
    SUM(paidamount) as total_paid_amount
FROM fees_transections;
```
**Acceptance Criteria:** `total_records` must equal 1,604; `total_paid_amount` must match within 0.00 BDT tolerance.

### 4.2 Checksum Query 2: Operational Expenditures
```sql
-- MySQL Source:
SELECT 
    COUNT(*) as total_vouchers,
    SUM(CAST(REPLACE(amount, ',', '') AS DECIMAL(15,2))) as total_expanses
FROM expanses
WHERE deleted_at IS NULL;

-- PostgreSQL Target:
SELECT 
    COUNT(*) as total_vouchers,
    SUM(amount) as total_expanses
FROM expanses
WHERE deleted_at IS NULL;
```
**Acceptance Criteria:** `total_vouchers` must match; `total_expanses` must match down to the exact paisa.

### 4.3 Checksum Query 3: Operational Incomes
```sql
-- MySQL Source:
SELECT 
    COUNT(*) as total_vouchers,

FROM incomes

-- PostgreSQL Target:
SELECT 
    COUNT(*) as total_vouchers,
```

## 5. Post-Migration Sequence Reset Verification

To ensure new insertions succeed immediately post-migration, execute sequence synchronization across all 52 tables:

```sql
DO $$
DECLARE
    row record;
BEGIN
    FOR row IN 
        SELECT table_name 
        FROM information_schema.tables 
        WHERE table_schema = 'public' 
          AND table_type = 'BASE TABLE'
    LOOP
        BEGIN
            EXECUTE format(
                'SELECT setval(pg_get_serial_sequence(%L, %L), COALESCE((SELECT MAX(id) FROM %I), 1))',
                row.table_name, 'id', row.table_name
            );
        EXCEPTION WHEN OTHERS THEN
            -- Skip composite tables without single id column
            CONTINUE;
        END;
    END LOOP;
END $$;
```

## 6. Rollback Strategy & Preconditions

### Preconditions for Migration Execution (Phase 3+):
1. **Full MySQL Cold Dump:** Complete `mysqldump --single-transaction --routines --triggers --hex-blob icbd_web > icbd_web_pre_migration_backup.sql` taken before any migration script is initiated.
2. **Staging Environment Validation:** The migration pipeline must be executed and validated 100% on a staging PostgreSQL database before production cutover.
3. **Application `.env` Rollback Plan:** If any validation check fails on production, `.env` database driver settings will be immediately toggled back to `DB_CONNECTION=mysql` with zero data corruption to the MySQL database.
4. **Maintenance Window:** Migration cutover must be scheduled during a dedicated 2-hour maintenance window with website maintenance mode enabled (`php artisan down`).
