## 1. Migration Strategy and Technical Feasibility

### 1.1 Architectural Target
- **Source Database:** MySQL 5.7 / MariaDB 10.4 / MySQL 8.0 (Storage Engine: InnoDB, Charset: `utf8mb4`, Collation: `utf8mb4_unicode_ci`).
- **Target Database:** PostgreSQL 15 / 16 (Encoding: `UTF8`).
- **Objective:** Complete schema modernization, strict typing, preservation of legacy auto-increment primary keys, preservation of file paths, and zero loss of historical student ledger records.

### 1.2 Fundamental Engine Differences & Behavioral Shifts
1. **Case Sensitivity:**
   - MySQL with `utf8mb4_unicode_ci` performs case-insensitive comparisons on `LIKE` operators by default (`WHERE sname LIKE '%sahab%'` matches `SAHAB`).
   - PostgreSQL `LIKE` is strictly case-sensitive. All search queries in [`StudentsController@active`](file:///c:/wamp64/www/innova-web/app/Http/Controllers/Admin/StudentsController.php#L85-L90), [`BlogController`](file:///c:/wamp64/www/innova-web/app/Http/Controllers/Admin/BlogController.php), and `FrontendController` must be updated to use `ILIKE` or `LOWER()`.
2. **Boolean vs. Tinyint Misconception:**
   - In MySQL, boolean flags are stored as `TINYINT(1)`.
   - **Critical Trap in `students.IsActive`:** In the `students` table, `IsActive` is NOT a binary boolean!
     - `1` = Active
     - `2` = Irregular
     - `3` = Completed
     - `4` = Restricted
     - `5` = Postponed
     Migrating `students.IsActive` to PostgreSQL `BOOLEAN` will destroy status data! It must be migrated to `SMALLINT`.
   - Binary flags (`IsRegister`, `status`, `IsActive` in `sessions`) should be migrated to PostgreSQL `BOOLEAN`.
3. **Date and Time Representation:**
   - MySQL permits zero dates (`0000-00-00 00:00:00`). PostgreSQL strictly rejects them.
   - Any legacy zero dates must be sanitized to `NULL` prior to ingestion.

## 2. Comprehensive Data Type Mapping Strategy

| MySQL 5.7/8.0 Data Type | Proposed PostgreSQL 15/16 Type | Justification & Transformation Rule |
|---|---|---|
| `BIGINT UNSIGNED AUTO_INCREMENT` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | Preserves existing primary key IDs during data import while automatically providing sequence generation for new records. |
| `INT UNSIGNED AUTO_INCREMENT` | `INTEGER GENERATED BY DEFAULT AS IDENTITY` | Standard sequence identity for integer keys. |
| `VARCHAR(191)` / `VARCHAR(255)` | `VARCHAR(191)` / `VARCHAR(255)` | Standard string representation. |
| `TEXT` / `LONGTEXT` | `TEXT` | PostgreSQL `TEXT` handles arbitrary length without performance penalty. |
| `VARCHAR` containing Currency Amounts | `NUMERIC(12, 2)` | Normalization: Strip commas (`REPLACE(..., ',', '')`), trim spaces, cast to decimal. Replace empty strings with `0.00`. |
| `TINYINT(1)` (Binary Flags) | `BOOLEAN` | Convert `1` → `TRUE`, `0` → `FALSE`, `NULL` → `FALSE`. |
| `TINYINT` / `INT` (Multi-state Enum Flags) | `SMALLINT` | Used for `students.IsActive` (`1..5`), `fees_transections.paymentType`, `fees_transections.channel` (`1=Cash, 2=bKash`). |
| `DATE` | `DATE` | Strict ISO format `YYYY-MM-DD`. Cleanse any zero dates (`0000-00-00`). |
| `TIMESTAMP NULL` | `TIMESTAMPTZ NULL` | Timezone-aware timestamps aligned with `Asia/Dhaka` (+06:00). |
| `JSON` | `JSONB` | Binary JSON indexing for setting payloads and metadata. |

1. `expanses.amount`

9. `dividend_withdraws.amount`
10. `investment_withdraws.amount`
11. `bank_loans.loan_amount`
12. `emi_installments.amount`

### 3.2 Cleansing ETL Pipeline Transformation Rule
Before inserting legacy strings into PostgreSQL `NUMERIC(12, 2)`:
```sql
-- Sanitization algorithm for legacy strings:
CASE
    WHEN amount IS NULL OR TRIM(amount) = '' THEN 0.00
    -- Strip currency symbols, commas, and trailing spaces
    ELSE CAST(REGEXP_REPLACE(TRIM(amount), '[^0-9.]', '', 'g') AS NUMERIC(12, 2))
END
```

## 4. Sequence Synchronization and Legacy ID Preservation

### 4.1 Sequence Reset Strategy
When migrating existing data into PostgreSQL using `IDENTITY` columns, sequences do not automatically increment to match the highest inserted ID.
After importing all tables, sequence synchronization must be executed for every table:
```sql
-- Pattern for every imported table:
SELECT setval(
    pg_get_serial_sequence('students', 'id'),
    COALESCE(MAX(id), 1)
) FROM students;

SELECT setval(
    pg_get_serial_sequence('fees_transections', 'id'),
    COALESCE(MAX(id), 1)
) FROM fees_transections;
```

## 6. Application Query Compatibility and Code Refactoring Requirements

### 6.1 Raw SQL Queries in Code
1. **[`ReportController.php:L57, L108`](file:///c:/wamp64/www/innova-web/app/Http/Controllers/Admin/ReportController.php#L57):**
   - **Current MySQL Syntax:**
     ```php
     DB::raw('REPLACE(expanses.amount, ",", "") AS amount_without_commas'),
     DB::raw('SUM(REPLACE(expanses.amount, ",", "")) as total_amount')
     ```
   - **Proposed PostgreSQL Syntax:**
     Once `amount` is migrated to `NUMERIC(12, 2)`, raw SQL string replacement becomes obsolete:
     ```php
     DB::raw('SUM(amount) as total_amount')
     ```
2. **Search Queries with LIKE vs. ILIKE:**
   - In [`StudentsController.php:L87-88`](file:///c:/wamp64/www/innova-web/app/Http/Controllers/Admin/StudentsController.php#L87-L88):
     ```php
     $q->where('sname', 'like', '%' . $search . '%')
       ->orWhere('phone', 'like', '%' . $search . '%');
     ```
   - Must be updated to:
     ```php
     $q->where('sname', 'ilike', '%' . $search . '%')
       ->orWhere('phone', 'like', '%' . $search . '%');
     ```
3. **Password Hashing Compatibility:**
   - **Verification:** Both MySQL and PostgreSQL store Bcrypt hashes as standard strings. The existing passwords in `admins` and `users` (which follow `$2y$10$...`) are 100% compatible with Laravel's Bcrypt hasher under PostgreSQL. Zero password re-hashing or migration friction required.
4. **Media and File Reference Paths:**
   - File references in `students.image`, `expanses.image`, `teachers.image`, `assets.image` are stored as relative strings (e.g. `'students/xyz.jpg'`).
   - Transferring these file paths verbatim into PostgreSQL preserves 100% of links to existing disk files in `storage/app/public/`.

## 7. Migration Risks and Open Verification Gaps

1. **Unverified Post-2024 Records:**
   - Because the local environment could not connect to the live database (`sroot` typo) and the committed SQL dump is from February 2024, the exact schema of tables created after Feb 2024 (`bank_loans`, `investment_withdraws`, `dividend_withdraws`) must be verified by dumping the live MySQL schema prior to running the migration.
2. **Orphan Records Risk:**
   - Because MySQL had foreign key enforcement disabled in some configurations (`'strict' => false`), existing records in `fees_transections` may reference `student_id`s that have been hard-deleted.
   - An ETL pre-check script must run:
     ```sql
     SELECT DISTINCT student_id FROM fees_transections WHERE student_id NOT IN (SELECT id FROM students);
     ```
     Any identified orphan records must be associated with a tombstone / dummy student record before foreign key constraints are applied in PostgreSQL.
